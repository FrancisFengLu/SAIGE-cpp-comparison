# C++ SAIGE port vs R SAIGE 1.5.1 — wall-clock benchmark

Run 2026-08-10 on the `visium-hd-worker` VM: **4 vCPU, 16 GB RAM, no swap.**

Reproduce with:

```bash
SAIGE_cpp_260716/step2_saige-step2/tools/run_bench_all.sh [data_dir] [out_dir]
```

Raw artefacts are preserved (one `/usr/bin/time -v` capture, one stdout log and
the exact YAML per run) under `tools/bench_timing_20260810/`:

| file | contents |
|---|---|
| `timings.csv` | every individual run: wall / user / sys / max RSS / output rows |
| `tables.md` | the tables in §3, regenerated by `summarize_bench.py` |
| `equivalence.txt` | the p-value comparison in §2.4 |
| `io_vs_compute.txt` | the setup-vs-compute split in §4 |
| `raw/`, `results/` | per-run logs, `/usr/bin/time -v` output, configs, output files |

---

## TL;DR

* **Region (gene-based) tests — the primary use case — C++ is 3.3× faster than R
  on 4 threads** (116 s vs 384 s) and **1.4× faster on 1 thread** (271 s vs 384 s).
* **Single-variant tests: C++ is 4.3× faster on 1 thread, 5.7× on 2** (2.2 s / 1.7 s
  vs 9.5 s). The C++ single-variant output is **bit-identical** to R's.
* **Step 1 (null model fit): the C++ is SLOWER than R.** 166 s vs 160 s at
  4 threads (0.96×) with BLAS pinned, and 159 s vs 118 s (0.74×) with BLAS at
  its default. Single-threaded it is 2.7× slower than R — but see §3.1, R's
  `nThreads=1` does not actually serialise R's step 1, so that comparison is
  not apples-to-apples.
* **Thread scaling of the C++ is mediocre**: region 2.33× on 4 threads (58%
  efficiency), step 1 2.03× (51%). The region test also spends **40–45% of its
  wall clock in system time** at every thread count.
* Equivalence: burden and SKAT p-values agree with R to ≤3e-12; the SKAT-O
  omnibus p-value disagrees by up to a factor of 1.9 on 4 of 2,853 results.

## 1. Benchmark dataset

Generated by `tools/gen_bench_data.py` (seed 21), stored at
`bench_data/N10000_g300/`:

| | |
|---|---|
| samples (N) | **10,000** |
| genes | **300** |
| rare variants per gene | 10–100, mean 54.7 |
| rare markers total (step 2 input) | **16,422** |
| common markers for the GRM (step 1 input) | 10,000, MAF 0.05–0.50 |
| region test sets produced | **2,853** (3 annotation masks × 3 max-MAF cutoffs × 300 genes + 300 Cauchy omnibus rows) |
| trait | quantitative, h² = 0.40, covariates x1 (continuous) + x2 (binary) |
| rare-variant MAF spectrum | 10^U(−4,−2), floored so MAC ≥ 1 |
| causal genes | 21 of 300 carry a burden effect (so the region test is not a pure null) |
| `wes.bed` / `grm.bed` on disk | 54 MB / 25 MB |

**Why this size.** *Memory was never the binding constraint* — peak RSS across
the whole benchmark was 458 MB (C++ region, 4 threads) and 443 MB (R region), on
a 16 GB box. **Wall-clock budget was the constraint.** A single R region-test run
at N=10,000 takes 6.4 minutes; the full matrix (2 BLAS phases × 3 stages × up to
3 thread counts × 2 engines × warm-up + 3 reps = 64 runs) took ≈3.5 hours as
specified. Going to N=50,000 or 500 genes would have multiplied that by 3–5×.

The gene count (300) and per-gene variant count (10–100) are at the low and full
end of the requested ranges respectively; both are realistic for a WES
gene-based analysis.

## 2. Methodology

### 2.1 What is being compared

| | R SAIGE 1.5.1 | C++ port |
|---|---|---|
| step 1 | `fitNULLGLMM(...)` | `saige-null -c cfg.yaml` |
| step 2 region | `SPAGMMATtest(groupFile=...)` | `saige-step2 cfg.yaml` |
| step 2 single | `SPAGMMATtest(...)` | `saige-step2 cfg.yaml` |

Drivers: `bench_r_step1.R`, `bench_r_step2.R` (argument mapping copied from
`test_data/loco_reference/run_reference.R` / `run_step2.R`), and the YAML
templates emitted by `bench_cpp_vs_r.sh`.

* **LOCO is off on both sides.** LOCO makes step 1 refit once per chromosome.
  Turning it off keeps the two engines doing identical work and keeps the
  benchmark inside the wall-clock budget of this box.
* **Step 2 uses one shared null model.** The R `.rda` from `fitNULLGLMM` is
  converted to the C++ `.arma` + `nullmodel.json` directory by
  `tools/rda_to_arma.R`, so both engines start from bit-identical `mu`, `res`,
  `V`, `X`, `XV`, `XVX`, `XVX_inv`, `XXVX_inv`, `XVX_inv_XV`, `S_a` and the same
  `varianceRatio.txt`. Any step-2 timing difference therefore cannot be caused
  by one engine having an easier null to start from, and any p-value difference
  is attributable to step 2 alone. Shared null: n = 10,000, p = 3,
  tau = (2.12016, 0.93375), variance ratio 0.3745.
* **Trait is quantitative,** Firth and the binary exact test are off, so neither
  engine can win or lose on a data-dependent fallback path.

### 2.2 Timing

Every run is wrapped in `/usr/bin/time -v`. Wall, user, sys and max RSS are
recorded for **every individual run**, not just the aggregate. `user/wall` is
reported because it is the direct read-out of parallelism actually achieved;
`sys` is reported because a large system time was the fingerprint of the
region-test memory bug fixed earlier in this project.

**Repetitions:** 1 warm-up + 3 measured per cell in Phase A (2 in Phase B). The
warm-up runs are listed separately at the bottom of `tables.md` and are
**excluded from every median, speedup and efficiency number**. Spread is the
min–max of the measured reps; with n=3 a standard deviation would be theatre.

The warm-up is done once per (stage, engine), not once per thread count: page
cache is per file and the input files are identical across thread counts. Doing
a full warm-up at every thread count would not have fit in the time budget.

### 2.3 BLAS threading — two separate tables

* **Phase A: `OPENBLAS_NUM_THREADS=1`.** The controlled measurement. Without it,
  4 OMP threads each spawning 4 BLAS threads oversubscribe a 4-core box and the
  thread-scaling numbers are meaningless.
* **Phase B: BLAS left at the machine default (4).** What a user who just runs
  the binary actually gets.

Our own parallelism comes from the `nThreads` / `fit.nthreads` config key, which
is independent of `OPENBLAS_NUM_THREADS`, so the two are genuinely separable.

### 2.4 The R build used

`code_copy/SAIGE_isolated` is **not** stock SAIGE 1.5.1 — it carries debug
instrumentation that `saveRDS()`/`write.csv()`s O(N) vectors on every step-1
iteration to a hard-coded path. Benchmarking against that would make R look
artificially slow. A de-instrumented copy was installed into a separate library
(`bench_data/Rlib_clean`; 25 instrumentation write calls neutralised, the
already-compiled `src/*.o` re-linked) and **all R numbers below come from that
clean build**. Sanity check on the pilot dataset: instrumented 7.38 s vs clean
7.42 s for the same step-1 fit, i.e. the instrumentation was not measurably
costing R anything at these sizes — the clean build is used regardless.

### 2.5 Equivalence check — are the two doing the same work?

From `equivalence.txt` plus a per-column breakdown:

**Single-variant, 16,422 markers:** 16,422 rows on both sides, **max |Δp| = 0**.
Bit-for-bit identical to R on the printed output.

**Region, 2,853 result rows** (identical row count and identical keys):

| quantity | max abs difference |
|---|---|
| `MAC`, `Number_rare`, `Number_ultra_rare` | **0** (identical — same markers, same ultra-rare collapsing, i.e. the same amount of work) |
| `BETA_Burden` | 1.0e-15 |
| `Pvalue_Burden` | 2.8e-12 |
| `Pvalue_SKAT` | 5.2e-13 |
| `Pvalue` (SKAT-O omnibus) | **1.5e-2** |

The disagreement is confined to the SKAT-O omnibus combination step (the ρ-grid
optimisation / Davies-tail mixing), not to the burden or SKAT components:

| abs log10(p) difference | rows out of 2,853 |
|---|---|
| > 1e-6 | 144 |
| > 1e-3 | 55 |
| > 1e-2 | 7 |
| > 0.1 | **4** |

Worst case: `GENE0175 / missense;lof;synonymous / maxMAF 0.001`,
C++ p = 6.88e-10 vs R p = 1.32e-09 — a factor of 1.9 in p, both far past any
exome-wide threshold. The *strongest* signals agree essentially exactly: the
five smallest p-values (1e-49 … 1e-61) match to |Δlog10 p| ≈ 2e-13.

**Threading does not change results:** C++ nThreads=4 output is bit-identical to
nThreads=1 (max |Δp| = 0 over all 2,853 rows).

### 3.1 Reading the tables — three caveats

1. **R's `nThreads` does not serialise R's step 1.** At `nThreads=1` R still
   burns 404 s of user time for 126 s of wall clock (user/wall = 3.2). Whatever
   that argument controls, it is not the OpenMP loop that dominates R's step 1.
   So the "step1 / cpp T=1 vs R T=1 → 0.37×" row is **not** a like-for-like
   single-thread comparison and should not be quoted as one. The honest
   single-thread statement is: *the C++ step 1 at 1 thread takes 338 s; R cannot
   be made to run step 1 on one thread through its public API.*
2. **R step 2 has no thread knob at all**, so the same R number is repeated
   against every C++ thread count in the "C++ vs R" tables.
3. **R's step-1 wall clock is oddly non-monotone** in `nThreads`
   (126 s at "1", 160 s at "4" in Phase A) — consistent with (1): the argument
   perturbs thread placement rather than the degree of parallelism.

### 3.2 Where the C++ is slower

Stated plainly, because it is a finding:

* **Step 1 is slower in C++ than in R at every setting measured.** 166 s vs
  160 s at 4 threads with BLAS pinned (0.96×), and 159 s vs 118 s with BLAS at
  default (0.74× — i.e. the C++ is 35% slower). The C++ step 1 also burns far
  more CPU to get there: 530 s of user time at 4 threads versus R's 418 s, for a
  *worse* wall clock. Something in the C++ step-1 parallel path costs ~60% extra
  total CPU relative to its own serial run (336 s serial → 530 s at 4 threads).
* **Single-variant scaling is negative past 2 threads:** 1.68 s at T=2 versus
  1.83 s at T=4. At 16,422 markers there is not enough work per thread to cover
  the overhead. This does not matter in absolute terms (both are ~2 s) but it
  means nThreads>2 is not useful for single-variant runs of this size.
* **Region-test system time is high at every thread count:** 44–52 s of the wall
  clock, i.e. 40–45% at T=4 and 17% at T=1. R's region test spends only 23–26 s
  in the kernel while doing the same work. This is the same signature (kernel
  time from allocation churn) that the earlier `max_markers_region` memory fix
  addressed, and it suggests there is more to recover there. Region peak RSS
  also still scales with threads: 107 MB → 221 MB → 446 MB for T = 1 → 2 → 4.

## 4. I/O versus compute

`saige-step2` is instrumented with `[TIMING]` phase markers, so the split is
directly measurable rather than inferred. From `io_vs_compute.txt` (Phase A,
rep 1):

| run | wall (s) | setup + I/O (s) | compute (s) | setup share |
|---|---|---|---|---|
| C++ region, T=1 | 261.8 | 0.07 | 261.7 | 0.03% |
| C++ region, T=4 | 117.0 | 0.07 | 116.9 | 0.06% |
| C++ single, T=1 | 2.14 | 0.06 | 2.07 | 2.8% |
| R region | 383.8 | 3.78 | 380.0 | 1.0% |
| R single | 8.92 | 2.47 | 6.45 | 28% |
| R step 1 | 150.9 | 2.45 | 148.4 | 1.6% |

For the C++, "setup + I/O" is YAML parse + null-model load + genotype-reader
open (`50_before_main_loop`); for R it is the process wall clock minus the
elapsed time `fitNULLGLMM`/`SPAGMMATtest` report internally, i.e. R interpreter
start-up plus `library(SAIGE)`.

**Conclusion: essentially all of the runtime on both sides is compute, not I/O.**
The C++ reads the 54 MB `wes.bed` and the null model in 70 ms. R carries a fixed
~2.5–3.8 s of interpreter/library start-up, which is irrelevant for the region
test (1% of runtime) but is 28% of its single-variant runtime — so part of the
"C++ is 4.3× faster at single-variant" headline is R start-up, not R's
per-marker work. On compute only, the single-variant ratio is 6.45 / 2.07 =
**3.1×**, and that is the number to quote if challenged.

`saige-null` is not `[TIMING]`-instrumented, so the step-1 split could not be
measured for the C++; its genotype read is the same order as step 2's (tens of
ms against ~160 s of fitting), so it is not material.

## 5. What could not be measured on this box

* **UK-Biobank scale (N = 100k–500k).** Not possible here. It is not a memory
  wall — peak RSS was under 0.5 GB — it is wall clock: a single R region-test
  replicate at N = 10,000 / 300 genes takes 6.4 min, and both engines scale
  roughly linearly in N for the score-statistic part. N = 500,000 with 20,000
  genes would be ≈ 50× the samples × 67× the genes ≈ 3,000× this run's cost for
  one replicate. A meaningful UKB-scale comparison needs a box with **≥ 32 cores
  and ≥ 64 GB**, and even there it is a multi-day job for R.
* **Thread scaling beyond 4 threads.** This machine has 4 vCPU. The region test
  is already at 58% efficiency at T=4, so the interesting question — does it
  keep scaling to 16 or 32 threads, or does the system-time overhead in §3.2
  dominate — cannot be answered here. Needs ≥ 16 cores.
* **Binary traits (SPA / Firth / ER exact test).** Only the quantitative path
  was benchmarked. Binary adds saddlepoint approximation and, for MAC ≤ 4, an
  exact test, and those are data-dependent branches where the R/C++ ratio could
  be very different. This is a real gap; it would cost roughly another 3.5 hours
  on this box to fill.
* **LOCO.** Off on both sides. LOCO multiplies step-1 cost by roughly the number
  of chromosomes and is the C++ port's headline correctness feature, but adding
  it would have put step 1 alone beyond the session budget.
* **A single-threaded R step-1 baseline.** Not achievable through R SAIGE's API
  (§3.1). It could be forced with an external `taskset -c 0`, which was not done
  here; that would be the correct way to get the number on a re-run.
