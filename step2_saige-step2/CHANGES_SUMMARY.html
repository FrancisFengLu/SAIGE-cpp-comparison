SAIGE step2 C++ - parallelization changes summary

Branch: step2-parallel · Final commit: 72a10ed · Tag: phase-final-shipped · Date: 2026-06-01 · Author: Francis Lu (Dana-Farber, Sethi lab) · Audience: Seokho Jeong (collaborator, UKB cluster)
TL;DR. Took the serial step2 marker loop and made it OpenMP-parallel across markers in five phases (A, B, D, E, C) plus two bug fixes and a PLINK/PGEN streamer. Phase A factored per-marker state into PerMarkerCtx; Phase B added nThreads: + thread-safe ER RNG + the #pragma omp parallel for; Phases D and "PLINK/PGEN streamer" removed the genotype read lock for BGEN/PLINK/PGEN (VCF still locked); Phase E parallelizes the outer region loop (SKAT/SKAT-O); Phase C wires in an optional matrix-level GEMM path (blockSize:) that is in place but not yet a win on this small test set (N=1000, ~128k markers). Best observed speedup on local laptop: ~2.3× at 4-8 threads in Wave 5; in the final shipped build with timing instrumentation, scaling is weaker (1.30× at 8 threads vs phase-B-D-fixed's ~2×) - hypotheses below. Code is correct, baselines match, and the design is ready for Seokho to test at UKB scale (N=400k) where the per-marker dot products are 400× longer and parallelism should pay off much more cleanly.

Note the regression. phase-final-shipped is slower than phase-B-D-fixed at every thread count, and scales weaker (1.30x at nT=8 vs ~2x). Suspects: Phase C bookkeeping overhead (PrefetchEntry + gVec copy even at blockSize=1), thread_local FILE* overhead in PLINK streamer for tiny per-marker reads, and possibly cache thrashing from N parallel FDs vs the kernel readahead that the single shared FD got.

4. Speedup hypotheses

H1 - Memory bandwidth saturation

Once ~4 threads are reading genotypes + doing BLAS, the DRAM bus is the bottleneck; additional threads compete on the same channel without adding throughput.
For: classic "speedup plateaus around 4 threads on consumer hardware" shape.
Against: dataset is small (N=1000) - working set fits in L2/L3, so DRAM may not be the limit yet.
Test: perf stat -e LLC-loads,LLC-load-misses,mem_load_uops_retired.l3_miss at nT=1,4,8; look for saturation in memory_bound.

H2 - Small dataset / tiny per-marker work

~128k markers / N=1000 means per-marker compute is ~30 us; OpenMP fork/join + chunk scheduling cost a non-trivial fraction of that.
For: Phase E (region loop) showed essentially zero speedup at nT=4 (1.02x) on the same dataset - tiny loop body.
Against: single-variant loop did get 2x at Wave 5 - so the work isn't that tiny.
Test: repeat with N=400k UKB data; per-marker work scales ~linearly in N, so should hit 6x+.

H3 - SMT non-acceleration

Test machine has 16 logical / 8 physical cores. SMT (hyper-threading) gives ~0% to compute/BLAS workloads; nT=16 should look ~ nT=8.
For: nT=16 is slower than nT=4 on compare (2.63s vs 2.14s) - SMT contention plus thread overhead.
Against: nothing - this is well-established.
Test: on UKB cluster cap nThreads at physical core count; pin with OMP_PLACES=cores OMP_PROC_BIND=close.

H4 - Phase C bookkeeping overhead even at blockSize=1

Phase C introduced a PrefetchEntry struct + a cache replay path; even when blockSize=1 the code still pays the prefetch buffer alloc + cache lookup + a gVec copy per marker.
For: phase-final-shipped is slower than phase-B-D-fixed at nT=1 (4.94s vs 4.12s, +20%) - a serial regression, not a parallel one. That points to Phase C or the PLINK streamer.
Against: if Phase C alone were the cause, the merge commit d12f549 would already show it. Need to bisect.
Test: compile with -DDISABLE_PHASE_C short-circuit; rerun config_compare nT=1. Or git-bisect between ef0ad23 and 72a10ed.

H5 - PLINK thread_local FILE* overhead

Each genotype read does a thread_local lookup, possibly opens the FD on first call, and uses its own stdio buffer. That's more work per read than the pre-streamer single-FD path, especially for small reads.
For: phase-final-shipped is the first build with the PLINK streamer; serial regression matches.
Against: thread_local lookup is ~ns; should not cost 0.8s over 128k markers (would imply ~6us per marker, which is plausible actually).
Test: tag the streamer with a runtime switch and rerun nT=1 with old single-FD path. Also try posix_fadvise(POSIX_FADV_SEQUENTIAL) on the thread_local FD.

H6 - Cache thrashing from N separate FILE*

Kernel page cache + readahead favor a single sequential reader. With N parallel readers each at different file offsets, readahead windows interfere and page cache lines get evicted by sibling threads.
For: known pattern on rotational disks and even NVMe with random offsets.
Against: .bed file is small (~64 MB for N=1000, 128k markers) and likely fully resident in page cache by run 2 - re-test from cold cache would be more informative.
Test: vmtouch -e plink.bed; ./step2_saige-step2 ... vs vmtouch -t plink.bed; .... Compare cold vs warm at nT=1 and nT=8.

H7 - Per-marker work imbalance

SPA / Firth / ER candidates take 10-100x longer than the cheap normal-approx path. Even with schedule(dynamic, 64) the tail markers can starve and leave one thread doing the heavy ones at the end.
For: standard load-imbalance pattern for SAIGE; documented in original paper.
Against: config_compare.yaml is quantitative trait, so no SPA/ER/Firth - this hypothesis applies to binary configs only.
Test: profile with OMP_DISPLAY_AFFINITY=true and a per-thread tick log; or use schedule(guided) / smaller chunk.

H8 - VCF residual lock (N/A here)

VCF still serializes via critical(genoread). Only PLINK quant config was profiled here, so this is N/A for the current numbers but worth flagging for Seokho if UKB uses BGEN+VCF.
For: n/a
Against: n/a
Test: run config_test_vcf.yaml at nT=1,4,8; expect no scaling.

H9 - False sharing on output vectors

Threads write to BetaVec[i], pvalVec[i], etc. at adjacent indices. Each element is 8 bytes; a 64-byte cache line holds 8 doubles. Adjacent is on different threads ping-pong the line.
For: classic false-sharing pattern; chunk=64 makes this less bad (each thread owns a contiguous 64-element span), but the boundary lines still ping.
Against: writes happen once per marker (~once per 30 us), not in a tight loop - unlikely to be a top-3 cost.
Test: pad to cache-line granularity (write into a thread_local buffer, flush in batches), or use perf c2c.

H10 - OMP fork/join + flush overhead at large nT

Each #pragma omp parallel for has setup/teardown costs that grow ~linearly with thread count; tiny inner work amortizes poorly at nT=16.
For: nT=16 regression (compare: 2.63s vs 2.14s @ nT=4).
Against: overhead is ~us, not seconds; would have to be hit thousands of times. Only one parallel for per single-variant marker loop, so probably not the main term.
Test: set OMP_WAIT_POLICY=ACTIVE and pin threads.

5. Recommended next steps (Seokho)

  • Run on UKB-scale N=400k (or even N=100k subset) - per-marker work grows ~linearly with N, so the parallel overhead becomes a much smaller fraction. Expect very different (better) ratios.
  • Try blockSize: 256 in YAML on the UKB run. The GEMM path should win when each per-column dot product is 400k rows - that's where the matrix view of step2 is meant to pay off.
  • Cap nThreads at physical core count (not logical) - SMT does not help compute-bound BLAS. Pin: OMP_PLACES=cores OMP_PROC_BIND=close OMP_WAIT_POLICY=ACTIVE.
  • Document what scaling actually looks like at UKB scale; that will tell us which hypothesis (H1-H10) is the real one and whether to invest in cleaning up Phase C / PLINK streamer overhead.
  • For BGEN at UKB scale, tune bgenReaderThreads / bgenDecoderThreads; the (4,8) regression we saw locally may flip the other way when decompression dominates.

8. Synthetic vs real data — what our benchmarks can/can't test

TL;DR. All three local stress tests (N=1k×128k, N=1k×2M, N=10k×200k) showed peak speedup 1.4–2.2× @ 8 threads; an N=50k attempt failed at Step 1 because plink2 --dummy data has no LD, which makes the sparse GRM pathological for PCG. The synthetic data also lacks the rare-variant tail and BGEN decompression cost — so candidate dispatch (SPA/ER/Firth) and BgenStreamer were never stressed. Real UKB-scale performance must be measured by Seokho on actual data.

8.3 What our tests can't tell us about UKB performance

✗ BgenStreamer's actual contribution (we tested only the PLINK path)
✗ Candidate-dispatch (SPA/Firth/ER) load-balance behavior (almost no candidates triggered)
✗ Sparse-GRM PCG path performance (no real LD)
✗ Multi-trait shared-decode benefit (no multi-trait support yet)

8.4 What our tests can confirm

✓ Numerical correctness — all multi-thread outputs are sorted-byte-identical with nT=1
✓ OMP integration produces a real speedup (~2× modest gain)
✓ Memory bandwidth caps scaling on memory-bound BLAS workloads
✓ SMT (>physical cores) provides no benefit, mild regression

8.5 Expected UKB-scale behavior (hypothesis)

  • BGEN decompression (CPU-bound, well-parallelizing): the streamer should be visible.
  • Larger per-marker compute amortizes OMP overhead.
  • 5–15% slow-path triggers stress candidate dispatch (load imbalance possible).
  • Sparse-GRM solves work properly (well-conditioned).
  • Expect 3–6× wall speedup at 8 cores; verification requires a real UKB profile.
